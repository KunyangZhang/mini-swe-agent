# Coding Agent Harness：把“能重启”做成可解释、可验收的恢复

## 项目要解决的问题

编码 Agent 的一次任务不只是几轮对话。模型可能已经回复，shell 可能已经改了文件，而进程恰好在结果保存前退出。直接从头运行有可能重复副作用；简单保存聊天记录又无法证明某条外部命令到底执行过没有。

项目围绕这个问题在 mini-swe-agent 上增加持久执行层。上游提供 Agent 循环、模型接口和执行环境；项目原有扩展用 SQLite 保存运行状态、模型回复、每条动作的意图和结果，使用单写者锁及配置绑定约束恢复。这些是已有能力。本次的工作是检查它们在真实状态组合下是否成立，并用代码修复与独立验收补齐证据。

## 第一阶段：先确认已有能力的真实范围

先核对 Git 版本、复现原有 98 项相关测试和七个故障位置，再运行原有 25 次重复脚本。175 次 durable 运行中 100 次自动继续、75 次暂停，没有重复计数器写入；25 次从头重启对照都产生重复写入。

这个结果支持“已知结果复用、未知结果暂停”的机制，却有两个局限：175 是运行次数，不是 175 种故障；暂停也不等于任务完成。因此后续没有继续堆重复次数，而是增加批次、预算、工作区和独立测试这些维度。

## 第二阶段：检查点必须保存一份语义完整的状态

第一处问题发生在“格式错误—成功动作—格式错误”这段流程。正常运行中，成功动作会把连续错误计数清零；原 durable 代码却先写 ready 检查点，随后才由外层循环清零。只要中断在两者之间，恢复后就可能把两次不连续错误累加，提前终止。

失败复现把中断精确放在 ready 落盘后。修复将清零移动到检查点之前，再证明恢复能够继续提交且已完成的 shell 不重跑。收获是：落盘本身不代表一致性；检查点需要对应一个完整的状态转移。

第二处问题是时间预算。原循环在下一次请求模型前检查总时间，但已保存的回复可以直接执行，三动作批次中后续动作也可能越过截止时间继续启动。两个失败复现分别覆盖“停机后预算到期”和“同批次第一条命令耗尽预算”。

这里不能简单在写入 intent 后检查时间，否则根本没启动的命令会被错误记成结果未知。最终实现先只读查询历史：已完成的结果可以复用，未知结果优先暂停，只有未开始的动作检查预算后再写 intent。修复后过期动作不产生新副作用；预算终止保留为终止结果，不算任务成功。

## 第三阶段：让任务结果独立于 Agent 自己的判断

新增一个真实 Python 修复任务：`chunked` 要支持迭代器、保留尾块、返回列表并拒绝非正块长。原文件在固定的 8 项测试中有 5 项失败。动作由脚本模型提供，但 shell、文件修改、pytest、进程退出与 SQLite 持久化都是真的。

实验把三条动作放在同一回复中：先查看代码并运行测试，再修改文件并追加补丁台账，最后运行测试；下一回复提交。这样能观察“多条动作中做到哪里”，而不只是数模型轮数。

| 尝试 | 实际观察 | 说明 |
|---|---|---|
| 补丁结果落盘后中断，再恢复 | 4 次工具执行、1 次补丁写入，8 项通过 | 已完成动作被复用，后续动作继续 |
| 结果均保存、观察检查点未保存时中断 | 同样 4 次执行、1 次写入 | 可以从结果重建观察，不需要重做外部动作 |
| 补丁生效、结果未保存时中断 | 自动恢复先暂停；核对源码、台账及测试后 resolve，最终完成 | 区分已知完成与无法判定的外部效果 |
| 同一位置用 DefaultAgent 从头运行 | 6 次工具执行、2 次补丁写入 | 最终测试通过仍可能存在重复副作用 |
| 外部将源码改回错误版后恢复 | Agent 提交，但独立测试失败 | 缓存中的成功测试不代表当前文件仍然正确 |

每个案例保留实际执行入口的 JSONL、补丁台账、源码状态、数据库状态与单独的验收结果。不会因为进程返回 0 或出现 Submitted 就记成功。人工核验由实验程序扮演操作员，明确标注为核验后恢复，未混入自动成功。

## 第四阶段：从负例追到一个可修复的工作区身份问题

外部文件变化不是本轮能普遍解决的问题，因此进一步检查更明确的边界：配置里的 cwd 是空值或 `.` 时，重启进程的启动目录变了，会发生什么？

在 A 保存回复，改到 B 恢复。旧配置字符串没有变，绑定检查通过，结果却在 B 执行 4 条命令并写入补丁，A 的原任务仍失败。绝对路径对照正常，说明问题是配置字符串没有表达实际目录身份。

修复让本地环境序列化解析后的绝对 cwd，复用现有配置指纹进行比较。现在错误目录会被拒绝；回到 A 能继续完成，B 无写入。新增两个失败复现和一个对照，使完整相关测试达到 107 项。原五条失败断言可直接用 Git 中的旧代码再次复现。

这个修复不解决同一路径中的任意文件漂移。保留这个区分很重要：已经修复的目录身份问题，与尚未解决的文件版本问题，有各自的证据和边界。

## 第五阶段：真实模型验证检验的是另一层能力

接入本地 Qwen2.5-Coder-3B-Instruct，用同一个小任务比较 Default 不中断、Durable 不中断、回复保存后恢复；再单独增加“初始源码与测试直接放进提示”的条件。两种条件各三次，全部达到 12 轮上限，未修好文件。

轨迹显示模型反复运行不匹配的 sed，并未正确使用提交协议；增加初始源码上下文也没有解决。两个恢复运行实际只请求 12 次模型，首个已保存回复没有重复请求，但任务仍失败。这支持恢复链路实际接入了模型，不能支持模型能力提高。

因此最终故事不是“让模型更聪明”，而是把执行语义与任务验收做清楚：哪些动作能复用，哪些必须核验，哪些配置不能混用，以及哪些成功状态必须接受外部测试检验。

## 面试时可以落到的工程判断

1. **为何不承诺 exactly-once？** SQLite 事务不能与任意 shell 或远端服务组成同一原子事务。存在“外部效果已发生，结果尚未落盘”的窗口；本项目选择暂停并显式核验。
2. **为何同时看执行次数与测试结果？** 测试通过不能发现所有重复副作用，零重复也不能证明任务做对。两类指标要分别验收。
3. **三个修复有什么共同点？** 恢复必须绑定完整状态：错误计数是控制状态，预算是执行条件，实际目录是环境身份。
4. **负面结果带来了什么？** 文件漂移暴露缓存的有效期问题，真实模型失败暴露策略能力与恢复能力的分离。它们直接限定了简历可以写到哪一步。

## 可直接使用的项目描述

基于 mini-swe-agent 补强持久执行 Harness，检查模型回复、动作意图与结果的恢复语义；建立五条修复前失败复现，修复错误计数持久化、待执行动作预算检查和实际工作目录绑定，相关回归达到 107 项。使用真实文件修改与 8 项测试验证批次中断、核验后继续和重复副作用对照，并保留工作区漂移及真实小模型编码失败的完整证据。
